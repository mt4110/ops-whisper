# ops-whisper 構想と事業優先度の検証

更新日：2026-10-08。**現在の目的は、小さな検索CLIをポートフォリオとして完成させること。** 以下には以前の実務・事業仮説も保持するが、需要検証を現在の完成条件にしない。実資料の解析、形式変換・OCRの実行、購入意向の確認は未実施。

既存rgで返却量・位置・件数・省略を制御する[最小CLI](SEARCH_CLI.md)と、[明示TOMLによる本文マスキング](MASKING.md)を個別承認の範囲で実装した。[SR-02の合成比較](evaluation/SEARCH_SYNTHETIC_TRIAL.md)も完了している。利用者は現機能で十分と判断し、アイデアの選別とマイルストーンの文書更新を承認した。実用性・販売可能性の証明と、ポートフォリオとしての完成を分ける。

## 1. 現在の判断

**現機能を固定し、PF-1「再現して説明できるポートフォリオCLI」で今回の機能開発を区切る。** OSS公開を選ぶ場合はPF-2の公開候補準備とPF-3の承認後公開へ進む。大型の資料解析基盤、対話review、構造パーサー、キャッシュを完成のために追加しない。

ポートフォリオとして示せるのは、既存rgの再利用、検索の全件数と表示上限の区別、全文から抜粋へのマスキング、期限と資源管理、失敗時の契約を、小さな実装と再現例へまとめたこと。一般的な業務効率改善や市場での優位を示した成果ではない。

以前の評価は、主に独立製品として投資する根拠を探していた。ポートフォリオという今回の目的には、購入意向や実ログの取得を必須にする必要がない。採用する案は既存機能の合成デモ・コード検索例・設計判断の説明に絞る。到達目標と終了条件は[マイルストーン](MILESTONES.md)、残作業は[実行タスク](TASKS.md)へ集約する。

| 判断 | 現時点の結論 | 判断を変える証拠 |
| --- | --- | --- |
| 小さなCLIを完成させるか | ポートフォリオとしてPF-1まで完成 | 現機能の不具合や説明・再現の不足があれば範囲内で修正 |
| OSSとして公開するか | PF-2準備とPF-3公開は未完了 | ライセンス等の準備と具体的な公開承認 |
| 独自変換・OCRや構造解析を作るか | 今回の完成条件に含めない | 現手段で答えられない一つの問いと別途の範囲判断 |
| 独立製品を作るか | 保留 | 複数の利用者に共通する不足、導入条件、支払意思 |
| 主力の時間を移すか | 根拠がない | 現主力の直近成果との比較と、継続便益の証拠 |

現在の主力の名前、作業時間・予算、実資料の利用権限は未確定であり、過去のプロジェクトから推定しない。**下記2〜9節は以前の実務・事業仮説の参照記録。** そこでの実務試験やDR/IR/OWの順序は再開時だけ用い、PF-1〜PF-3の前提にしない。過去の「試用未実施」は当時の代替ツール・実案件についてであり、その後の自作searchの合成検証は上記の記録を参照する。

## 2. 初期の伏字構想で想定した仕事

構想時には、開発者が障害の一部を同僚・製品サポート・AIへ説明する直前を想定していた。補足された実務は、ログそのものの共有より、その先のインフラ分析結果の提出である。想定と実務を同一視しない。

実務の流れは「許可された資料の収集 → 稼働・用途の解釈 → 結論と根拠の対応付け → 提出物の編集・確認 → 提出」。ops-whisperが直接扱うのは、最後の編集・確認に含まれる伏字と別名化だけ。資産の発見、稼働判定、用途推定、根拠の正しさは扱わない。

確認した負担は下表の二行目である。他の二つと混同しない。

| 負担の中心 | 最小の対応案 | ops-whisperの判断 |
| --- | --- | --- |
| 稼働状態・用途を読み解く | 既存資料・ログに対する問い、観測期間、判断根拠を整理 | 本体実装を進めない。伏字では解決しない |
| 分析結果と証拠を提出物へまとめる | [インフラ調査報告の記録型](evaluation/INFRA_REPORT_TEMPLATE.md)を一件で使う | 別のソフトウェアを作らず、まず文書で解決する |
| 提出時に同じ識別子や秘密を何度も伏せる | 既存エディタ・専用ツールと比較 | ここに具体的な不足が残る場合だけ候補を維持 |

提出物全体の正しさをマスキング結果で保証しない。ログに現れたことは、その観測条件下の証拠になるが、ログにないことだけでは停止・未使用とは断定できない。用途の説明は観測事実、設定や担当者の説明、推定を区別する。

今回の報告作業の完了条件は、受け手が結論から根拠と観測条件へ辿れ、未確認事項と次の確認先を理解できること。以下の伏字に関する仮定は保留した構想の記録であり、今回の負担の説明には使わない。

| 仮定 | 崩れる場合 | 先に確認すること |
| --- | --- | --- |
| 同じ識別子を何度も直している | 数行を一度直すだけならエディタで十分 | 実際の反復操作と、既存の一括置換で残る手間 |
| 別名で関係を残すと役立つ | IPや名前の同一性より具体的な値が調査に必要 | 共有後に答えたい質問と、残す必要のある値 |
| CLIが一番使いやすい | 選択・検索・修正が端末で難しい | 既存エディタと比べた一作業の完了しやすさ |
| 自動検出で確認が軽くなる | 誤検出修正と未検出の再読で負担が増える | 検出器だけの速度ではなく確認完了までの時間 |
| ローカル処理なら共有できる | 顧客規則が匿名化後の外部共有も禁止 | 編集の便利さと共有権限を混同していないか |
| 自分が使えば販売にもつながる | 低頻度・代替無料・組織調達が重い | 再利用と購入意思を別々に確認する |

初期対象に含めない利用者は、常時DLP、監査証明、医療・法令適合、中央管理、ログ基盤への自動投入を求める組織。これらに対応し始めると、今の一作業を越えて権限管理・更新配布・運用保証の製品になる。

## 3. 初期の伏字構想と既存代替の重なり

「文書上の機能」は確認できた事実として扱う。安全性・精度・導入容易性・実機での使いやすさは、この調査では検証していない。スター数やテスト数を採用理由にしない。

| 選択肢 | 一次資料で確認した範囲 | ops-whisperへの意味 |
| --- | --- | --- |
| 既存エディタ | VS Codeは範囲内の検索・置換などを持つ | 既知の数語を伏せるだけなら最も軽い比較相手。[公式資料](https://code.visualstudio.com/docs/editing/codebasics) |
| Privsan | オフラインCLI/TUI、カスタム置換、仮名化、確認して出力する操作 | 最初に比較する直接代替。実行前に版と対象を固定する。[固定版README](https://github.com/alakulo/privsan/blob/7585bca2d0e5b5ca96ce1ac1479822b0ce97e626/README.md) |
| jfr-redact | テキストの伏字、同一値の仮名化、単語を選ぶ操作 | Java系ログなら追加の比較対象。単語の抽出や一貫した別名自体も独自機能ではない。[固定版README](https://github.com/parttimenerd/jfr-redact/blob/bb17e73c36e4ec20f3ba6e75cfad87fa0929815a/README.md) |
| Presidio | 検出結果の範囲を使い、置換・マスク等を行うライブラリ | 変換の考え方の参考。今回の限定操作に対する導入負担は別評価。[公式資料](https://presidio.dataprivacystack.org/anonymizer/) |
| Gitleaks / Betterleaks | stdin等からの秘密検出。後者にはSDKもある | 検出部の再利用候補であり、操作全体の価値の証明にはならない。[Gitleaks](https://github.com/gitleaks/gitleaks)、[Betterleaks](https://github.com/betterleaks/betterleaks) |

### Privsanから具体的に残る比較課題

確認した版では、プレビューは非選択の検出値も隠すが、出力の置換対象は選択状態で決まる。カスタム置換時のプライバシーマスクも、表示と出力では適用範囲が異なる。この区別は公式ガイドに記載されている。[固定版TUIガイド](https://github.com/alakulo/privsan/blob/7585bca2d0e5b5ca96ce1ac1479822b0ce97e626/docs/TUI.md)

ソースでも`Render(..., all)`が選択状態を分け、置換プレビューに追加マスクを作る処理を確認した。これは仕様と実装の静的な照合であり、脆弱性の断定や実行結果ではない。[model.go](https://github.com/alakulo/privsan/blob/7585bca2d0e5b5ca96ce1ac1479822b0ce97e626/internal/model/model.go)、[replace.go](https://github.com/alakulo/privsan/blob/7585bca2d0e5b5ca96ce1ac1479822b0ce97e626/internal/tui/replace.go)

ここから立つ仮説は「秘密候補の処理と案件固有の置換を一つの最終下書きへ合成し、確認した本文をそのまま出すと、再確認の負担が減る」である。仮説が成立しても、既存ツールへの改善提案で済む可能性がある。別リポジトリを持つことは自動的な結論ではない。

### Veil Clipとの重複

2026-10-08にローカルのVeil ClipのREADMEと`src/detector.rs`を確認した。HEADは`b70d6f62cb765261e924b7b8c3c9784a8b88d122`、確認した作業ツリーは変更なし。READMEは開発・公開準備の凍結を記載している。

その検出器はAWSアクセスキーID形式と秘密鍵ヘッダーの有無を返す。置換に必要な本文範囲を返さず、鍵本文のマスクにもそのまま使えない。設計上の参考にはできるが、共通ライブラリ化や凍結プロジェクトの再開をops-whisperの前提にしない。

## 4. 現設計で修正する点

| 問題 | 利用者への影響 | 改訂方針 |
| --- | --- | --- |
| 最初の例がTOML準備を要求する | 数語を置換するための準備が手作業より重くなる | その操作内だけの文字列指定を先にする。ルールファイルは任意 |
| 全下書きの確認しかなく、範囲を絞れない | 大量の不要な内容をレビューする | 一つの連続した行範囲を選択可能にする。自動要約はしない |
| 秘密候補を非機密として残せない | 誤検出で説明に必要な値が消え、ツールを避ける誘因になる | 個別候補に限定した明示的な保持判断を設計。既定はマスク、永続許可はしない |
| Unicodeスカラー位置を人に入力させる | 日本語・結合文字・伏字後の位置で誤操作しやすい | 検索・候補番号で対象を選び、内部だけで原文座標へ対応付ける |
| 大きいコアとOS対応がレビュー体験より先 | 価値がないと分かるまでの投資が増える | 合成入力で一作業を通す最小経路を早く作り、拡張前に確認する |
| 改行保持と複数行マスクの関係が未定義 | 秘密鍵などの置換で行番号・文脈を壊す | 複数行範囲をマスクする場合も元の改行列を保持する |
| 全親symlink拒否の要求が粗い | macOSの一般的なパスでも使用不能になり得る | 開いた親ディレクトリを基準に作成し、最終要素の競合を拒否する |

個別候補の保持は「検証失敗を無視して出力する」機能ではない。検出失敗・不正な範囲・上限超過は引き続き出力を阻止する。人が検出候補を非機密と判断することと、プログラムが処理を完了できないことを分ける。

## 5. 加えるアイデアと採否

| 案 | 判断 | 検証したい効果 | 採用しない条件 |
| --- | --- | --- | --- |
| 共有する連続行範囲を先に選ぶ | 条件付きの最小実装へ含める | 不要な共有とレビュー量を減らす | エディタの切り出しで十分、必要な文脈を失う |
| 一つの値を選び、同じ値をまとめて別名化する | 条件付きの最小実装へ含める | TOMLや同じ入力の反復を減らす | 一括置換より手間が増える |
| 秘密候補・別名・手動マスクを同じ下書きへ合成する | 設計の必須条件 | 置換の段階を分けて取りこぼす負担を減らす | 既存ツールの設定や小変更で同じ作業が完了する |
| 確認本文と出力本文の一致、変更箇所の追跡 | 設計の必須条件 | 何を出すかを判断しやすくする | 実装しても確認の負担が減らず、採用理由にならない |
| 出力直前の同一検出器による再確認 | 小さな検証として採用 | 置換合成で生じた新しい候補や未解決候補を見つける | 別の巨大検出エンジンや無限再走査が必要になる |
| 共有先別の保存プロファイル | 保留 | 同じ組織の同じ規則を繰り返す場合の時短 | 初回設定・実名保存の負担の方が大きい |
| 相対時刻化・パス階層の部分保持 | 保留 | 実値を減らし調査上の関係を残す | 別の時刻・パスと突き合わせる調査を壊す |
| JSON/CSVの構造を保った編集 | 保留 | フィールド指定の負担軽減 | 初期の共有作業がプレーンテキストで済む |
| ローカルGUI・エディタ拡張 | CLI比較で必要なら再判断 | 選択と誤検出修正の直接操作 | 配布・保守の負担が便益を上回る |
| 結論・根拠・観測期間・未確認点を結ぶ報告の型 | 実務に近い小さな代替案として追加 | 分析の説明を追跡しやすくする | 既存の提出様式で十分なら独自様式も不要 |
| 安全スコア、認証済みラベル | 不採用 | 有効な保証範囲を定義できない | 検出件数を安全性に変換しない |
| 対応表の保存、返答の実名復元 | 初版では不採用 | 機密を復元する別経路と保守負担が増える | 基本用途の成立前には扱わない |
| LLMプロキシ、MCP、自動送信、中央管理 | 今回は不採用 | 元の仕事と異なる運用・権限が必要 | 独立した需要なしに拡張しない |

「条件付きの最小実装へ含める」は、M0を通過して実装が承認された場合の範囲を示す。今回それらの実装を開始した意味ではない。

## 6. 技術選択と保守の負担

言語を先に決める必要はない。既存ツールを採用できれば本体言語の選定自体が不要になる。独立実装の場合は、必要形式を既存検出器で扱えるか、原文の正確な範囲が得られるか、オフラインで動作を閉じられるかを先に確認する。

Gitleaksは新機能追加終了・セキュリティ修正中心という方針を示し、Betterleaksには追加の認証情報確認機能がある。どちらも名前から今後の保守性やネットワーク無効の既定値を推定しない。固定版の契約確認を行う。[Gitleaksの方針](https://github.com/gitleaks/gitleaks)、[Betterleaksの機能](https://github.com/betterleaks/betterleaks)

必要形式が少数なら、明示した既存ルールの再利用で足りる可能性がある。ただし、それを「独自検出器を作っていないから無料」と扱わない。形式更新、誤検出、依存更新、OS互換性、Issue対応は継続費用である。共通基盤・プラグイン・二言語化は初期には設けない。

## 7. 参考：事業上の優先度

個人の作業時間が減ること、OSSとして使われること、継続収益が得られることは別の成果である。

- 自分だけが低頻度で使うなら、既存ツールの設定や小さな手順書が妥当な完成形になり得る。
- 他の開発者も繰り返し使うなら、限定されたOSSとして公開する理由になる。利用者数だけでは支払意思を示さない。
- 組織が買うなら、購入者、配布・更新・利用ルール、窓口、責任範囲を確かめる必要がある。今の単発CLIに管理機能を足す前に、その費用を負担する具体的な相手が必要。
- 業務委託で自分が楽になることはランウェイへの間接効果であり、自分のプロダクト収益とは分けて記録する。

時間面の判断には、同じ期間で「実際の利用回数 × 一回あたりの確認完了までの短縮時間」と「初期導入・設定・保守時間」を比較する。一回の短縮時間には誤検出修正と再確認も含める。値が未取得のため、改善率や損益分岐の回数は算出しない。リスク低減額を推測で売上へ足さない。

現在の主力の次のリリース・販売・ユーザー検証を遅らせる必要があるなら、ops-whisperは保留する。実装時間の上限と終わりを合意するまでは、後続タスクへ日付や確定見積りを付けない。

## 8. 参考：実務研究を再開する場合の終了条件と意思決定

以前の問いは「散在資料から根拠を辿れる要件・暫定設計を作る手戻りが減るか」。主力への接続は、業務の反復負担を小さくして時間を取り戻せるかだった。業務委託の効率化と、自分の製品の継続収益は別に判断する。現在のポートフォリオ完成とは別の研究経路である。

以前の拡張範囲の机上整理は、手順・記録型・代替・失敗条件・タスクを定義した時点で終了した。この研究を別途再開する場合だけ、DR-01で一つの設計対象と作業枠を確定し、DR-02〜DR-04で棚卸し・要件整理・暫定設計を作り、DR-05で採否判断をする。入力と権限が決まらなければ実案件へ進まない。未決事項に人の判断が必要なことを理由に、さらに自動化機能を増やさない。

以下は伏字構想を将来再評価する場合の条件である。比較対象は既存エディタとPrivsanを基本とし、Java/JFRが実際の用途の場合だけjfr-redactを追加する。一つの代表作業で足りるかを先に判断し、形式を増やして無理に不足を作らない。

結果は次のいずれかに分類する。

1. **既存手段を採用**：作業が完了し、確認負担も許容できる。独立実装を終了し、必要ならローカル手順だけ残す。
2. **既存手段の小改善**：不足が文言・既定値・一操作に閉じる。改善案を準備し、外部Issue/PRの投稿は別途承認範囲で扱う。
3. **限定実装**：反復負担が残り、今回の4点で解決できる見込みがあり、技術契約・作業枠を満たす。承認後に一作業を通す実装へ進む。
4. **保留・終了**：利用場面が発生しない、主力を遅らせる、確認負担が減らない、実装が別の解析研究へ広がる。

## 9. 証拠の限界
