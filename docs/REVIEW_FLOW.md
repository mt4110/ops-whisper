# ops-whisper レビュー操作の紙上案

状態：保留した伏字CLIの未実装の操作案。現在の優先対象は[結論と証拠を対応付ける報告手順](INFRA_REPORT_WORKFLOW.md)。CLIの実行結果・利用者試験ではない。最小の不足を比較するために使い、画面案の見栄えを価値の証拠にしない。

## 入力と目的

以下は全て合成データ。目的は「同じホストへの再試行が失敗したことを説明する」。案件名とホスト名は別名にし、認証値は伏せ、ステータスと順番を残す。本例の秘密候補は紙上の入力条件として与えるもので、未選定の検出器が検出した結果ではない。

```text
healthcheck status=200
client=ExampleCo host=api.internal.example user=sample-user
Authorization: Bearer sample-secret
retry host=api.internal.example status=503
retry host=api.internal.example status=503
healthcheck status=200
```

## 操作A 共有範囲と一回限りの別名

1. 入力と新規出力先を指定して開始する。設定ファイルの準備は不要。
2. 全入力を上限内で検出した後、共有する行範囲を2〜5に指定する。複数行秘密の範囲は選択境界で切れてもマスク対象にする。
3. レビュー画面で案件名をリテラル検索し、候補を選んでCLIENT別名化する。同じ範囲内の一致をまとめて提案し、対象件数を表示する。
4. 同じ方法でホストとユーザーを指定する。入力は対話内で行い、値をコマンド引数やシェル履歴に残さない。
5. 秘密候補のマスク、別名、手動変更を合成した本文を確認する。

```text
client=<CLIENT_1> host=<HOST_1> user=<USER_1>
Authorization: Bearer <REDACTED>
retry host=<HOST_1> status=503
retry host=<HOST_1> status=503
```

最終確認には選択範囲、変更件数、明示保持件数、出力先の操作内ラベルを表示する。行番号・件数・操作案内は本文へ混ぜない。確認した本文だけを出力する。出力先の実パスは起動時に利用者が指定し、診断や共有本文には含めない。

確認する問いは、エディタの切り出しと一括置換より少ない負担で完了したか、残した情報で元の質問に答えられるか、Privsanの操作と比べて再確認が減るか。これらは未測定である。

## 操作B 誤検出を個別に修正

ある候補が非機密のエラー識別子だった場合を、検出器に依存しない合成の候補で確認する。

1. 候補の理由と周辺文脈を見る。既定では値を伏せる。
2. 必要なら、その候補だけをローカル画面に表示する操作を明示して行う。スクロールバックに残る可能性を伝える。
3. 非機密と判断した候補について、今回のこの出現だけを保持する。別の出現や次回へ自動適用しない。
4. 最終本文では保持する値を実際に表示し、保持件数を通知する。画面だけ伏せた値を出力へ戻すことはしない。
5. 修正後は前の承認を破棄し、再確認する。手動マスクが同じ場所に残るならマスクが優先する。

全件を一度に許可する操作や「安全」表示を作らない。検出失敗や不正な範囲は、この操作で解除できない。

## 操作C 候補ゼロと取消

候補ゼロでも、選択した本文を確認できる。機密がないとは表示しない。利用者は追加マスク、範囲修正、出力、取消を選ぶ。

EOF/Ctrl-C/取消では、出力開始前なら本文・ファイルを出さない。出力開始後の中断では部分ファイルの可能性を伝える。ファイルを勝手に削除しない。
